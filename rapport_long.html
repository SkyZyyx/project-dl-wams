Résumé

Ce rapport décrit le projet Apex Motors de façon détaillée. Le système est organisé en plusieurs services Django séparés. Chacun a un rôle précis : authentification, catalogue, commandes, recherche visuelle et passerelle principale. Le but est de garder le code lisible, de faciliter le déploiement local et de montrer une vraie séparation entre la logique métier et la partie intelligence artificielle.

Le projet ne se limite pas à un CRUD classique. Il ajoute une recherche par image avec embeddings et Qdrant, des règles de permission basées sur le rôle utilisateur, des commandes avec snapshots, et une orchestration complète avec Docker Compose et Nginx.

1. Introduction et contexte

Apex Motors est une application e-commerce de démonstration centrée sur les voitures et les produits liés à l'automobile. Le projet montre comment construire une plateforme plus réaliste qu'un simple monolithe. L'application est découpée en plusieurs services indépendants pour éviter que tout le code soit mélangé dans un seul endroit.

Cette approche a un intérêt pédagogique fort. On voit comment séparer les responsabilités, comment faire communiquer plusieurs API REST, comment gérer des bases de données distinctes, et comment intégrer une brique de recherche intelligente sans alourdir le reste du système.

Dans les documents de référence du dépôt, le même esprit apparaît : architecture distribuée, services nommés clairement, proxy public, bases séparées et parcours utilisateurs bien définis. Le projet ressemble donc à un mini-système de production.

2. Méthode d'analyse

Pour préparer ce rapport, j'ai d'abord parcouru la structure du dépôt afin de comprendre les services présents et leurs responsabilités. J'ai ensuite lu les fichiers de configuration, les vues, les serializers, les permissions, les modèles et les scripts de déploiement. J'ai aussi extrait le contenu des deux rapports PDF de référence pour m'inspirer du style académique et de l'organisation des chapitres.

Cette manière de travailler permet de rester proche du code réel. Le rapport ne décrit pas une architecture imaginée : il suit ce qui est effectivement implémenté dans le dépôt. Cela évite les généralités et permet d'expliquer le rôle de chaque fichier utile.

J'ai surtout cherché quatre choses : comment le système s'initialise, comment les services échangent des données, comment les rôles utilisateur sont appliqués, et comment la recherche visuelle est construite de bout en bout.

3. Vue globale de l'architecture

Le dépôt utilise cinq services applicatifs principaux : main_service, user_service, product_service, order_service et search_service. Chaque service a sa propre base PostgreSQL. En plus de cela, Qdrant stocke les vecteurs d'images et Nginx sert de point d'entrée public.

Le choix de plusieurs bases séparées est important. Il évite les dépendances directes entre les tables des différents domaines. Par exemple, order_service ne lit pas directement les tables du catalogue. Il interroge product_service via HTTP, puis stocke ses propres snapshots.

Cette séparation rend le projet plus clair. On sait exactement où se trouve chaque responsabilité. Les données utilisateurs restent dans user_service, les produits dans product_service, les commandes dans order_service, et la recherche vectorielle dans search_service + Qdrant.

user_service8001Authentification et profils
product_service8002Catalogue et images produits
order_service8003Commandes et snapshots
search_service8004Recherche visuelle et embeddings

4. Service d'authentification

user_service est le service responsable des comptes. Son rôle est simple mais central : créer les utilisateurs, gérer les profils et produire des tokens JWT. Le modèle UserProfile ajoute un champ role avec trois valeurs : admin, seller et client.

Le token JWT est enrichi avec le rôle et le nom d'utilisateur. C'est un choix pratique, car les autres services peuvent vérifier les droits sans appeler user_service à chaque requête. On garde ainsi une authentification stateless, plus adaptée à un système distribué.

/api/auth/login/POSTObtenir un token
/api/auth/profile/GETLire le profil

5. Service catalogue

product_service est le cœur métier du catalogue. Il gère les catégories, les produits et les images associées. Le modèle Product contient le nom, la description, le prix, la catégorie, le vendeur et la date de création. Le modèle ProductImage conserve l'image, une miniature base64, un indicateur d'image principale, l'état d'indexation et l'identifiant Qdrant.

Un détail intéressant est la génération de miniature dans le modèle. Le fichier image est ouvert, corrigé si nécessaire, redimensionné, compressé et converti en base64. Cela permet d'avoir un aperçu rapide sans charger tout le fichier dans l'interface.

Le service applique aussi des permissions métier. Un seller peut écrire dans le catalogue, mais un client ne le peut pas. En plus, un produit peut être modifié seulement par son propriétaire vendeur. C'est une règle simple, mais importante pour maintenir la cohérence des données.

class ProductSerializer(serializers.ModelSerializer):
    images = ProductImageSerializer(many=True, read_only=True)
    image_files = serializers.ListField(child=serializers.ImageField(), write_only=True, required=False)

    def validate(self, attrs):
        image_files = attrs.get("image_files") or []
        if self.instance is None and len(image_files) < 5:
            raise serializers.ValidationError({"image_files": "Provide at least 5 images when creating a product."})
        return attrs

Cette validation montre une règle métier claire : la création d'un produit demande au moins cinq images. Le but est d'améliorer la recherche visuelle et d'avoir un catalogue plus riche.

6. Service commandes

order_service gère les commandes de manière indépendante. Il enregistre l'utilisateur, la date, puis les lignes de commande avec des snapshots complets du produit. Cette méthode protège l'historique si le produit est modifié ou supprimé plus tard.

Le service utilise une transaction atomique. Cela veut dire que la commande entière est créée ou bien elle échoue complètement. C'est un point essentiel pour éviter les commandes partiellement enregistrées.

Au moment de la création, le service récupère les produits nécessaires depuis product_service. Il ne copie pas seulement l'identifiant produit, mais aussi le nom, la description, la catégorie et le prix unitaire. Le résultat est plus stable et plus lisible pour l'utilisateur final.

7. Service recherche

search_service est la partie la plus technique du projet. Il reçoit des images, les vérifie, les prépare, calcule des embeddings et interroge Qdrant pour retrouver des produits similaires. C'est la brique qui donne au projet son aspect intelligent.

Le pipeline est découpé en étapes simples : contrôle qualité de l'image, preprocessing, embedding, recherche vectorielle, filtrage et réponse finale. Cette découpe rend le code plus facile à suivre et plus facile à modifier si le modèle change.

Le service ne renvoie pas les fiches produits complètes. Il renvoie surtout des identifiants, des scores et des métadonnées. Ensuite, main_service récupère les détails du catalogue et reconstruit la réponse finale pour l'interface.

RouteMéthodeRôle
/api/index/POSTIndexer une image produit
/api/search/POSTRechercher une image similaire
/api/index/<product_id>/DELETESupprimer les vecteurs d'un produit
def search_image(image_bytes, limit=10, score_threshold=None, model_id=None):
    ok, reason = validate_image_quality(image_bytes)
    if not ok:
        return {"detail": reason}
    vector = get_embedder(model_id).embed(preprocess_image_bytes(image_bytes))
    results = search_vectors(vector=vector, limit=limit, score_threshold=score_threshold, model_id=model_id)
    return {"matches": results}

Ce morceau illustre bien la logique générale. Le code reste compact, mais il couvre la chaîne complète de recherche, de l'entrée image jusqu'au résultat exploitable.

8. Communication entre APIs

La communication entre services se fait presque toujours par HTTP et par APIs REST. Le projet évite de partager directement des modèles Django entre services. C'est une bonne pratique dans une architecture microservices, car chaque domaine reste indépendant.

main_service joue un rôle de passerelle. Le navigateur parle surtout à lui, puis il contacte user_service, product_service, order_service ou search_service selon l'action demandée. Cela donne une seule porte d'entrée côté interface.

Quand une image est envoyée pour la recherche, main_service appelle search_service, puis récupère les produits par leurs identifiants via product_service. Ce mécanisme d'hydratation est important : il transforme une réponse technique, centrée sur les vecteurs, en réponse métier lisible.

Le même principe existe pour les commandes. order_service interroge product_service pour obtenir des données fraîches, puis les copie dans ses propres tables. Ici encore, l'API sert de frontière entre les domaines.

9. Sécurité et permissions

Le projet applique une sécurité simple mais utile. Les rôles sont transmis dans le JWT. Les services utilisent ensuite ce rôle pour autoriser ou refuser certaines actions. Cela évite de réécrire la logique d'accès dans chaque service.

Dans product_service, les droits d'écriture sont réservés aux vendeurs. Dans order_service, seuls les clients peuvent passer une commande. Cette règle est cohérente avec l'utilisation attendue de la plateforme.

Les permissions sont pensées pour être lisibles. Le code ne cherche pas à faire une sécurité trop compliquée. Il s'agit plutôt d'une sécurité suffisante pour un projet académique ou de démonstration, avec une base propre pour aller plus loin si besoin.

class SellerWritePermission(BasePermission):
    def has_permission(self, request, view):
        if request.method in SAFE_METHODS:
            return True
        return _is_seller(request)

class ProductOwnerPermission(BasePermission):
    def has_object_permission(self, request, view, obj):
        return _is_seller(request) and obj.seller_username == _username(request)

Ces classes montrent une logique claire : lire est autorisé plus largement, écrire est contrôlé, et la propriété du produit est vérifiée au niveau objet.

10. Déploiement Docker

Le déploiement local repose sur Docker Compose. Chaque service a son image, son port, ses variables d'environnement et son volume si nécessaire. Le compose démarre aussi les bases PostgreSQL, Qdrant et Nginx.

L'intérêt de cette structure est de pouvoir lancer tout le système avec une seule commande. Le projet devient alors facile à tester, à démontrer et à redémarrer proprement.

Les noms réseau internes sont importants. Dans les conteneurs, localhost ne désigne pas la machine hôte, mais le conteneur lui-même. Le compose utilise donc des alias réseau comme userservice, productservice, orderservice et searchservice.

Les volumes gardent les données, les images et les vecteurs. On sépare aussi les bases pour que chaque service conserve son autonomie.

Ce petit extrait résume l'idée du déploiement : des services indépendants, mais reliés par des URL internes stables.

11. Parcours utilisateur

Le parcours principal démarre par la page publique servie par Nginx puis par main_service. L'utilisateur peut se connecter, parcourir le catalogue, consulter les détails d'un produit, uploader des images en tant que vendeur et lancer une recherche visuelle.

Le frontend est volontairement simple. Il n'y a pas une grosse application SPA séparée. Le projet garde une logique Django classique, avec des templates et un peu de JavaScript. Cela colle bien à l'objectif de démonstration.

Le parcours vendeur est un peu plus riche. Il peut créer des produits avec plusieurs images, ce qui alimente ensuite la recherche visuelle. Le parcours client, lui, se concentre sur la découverte des produits et la commande.

Ce découpage permet de montrer deux rôles différents dans la même plateforme, avec des droits différents et des interfaces adaptées.

13. Tests et validation

Le dépôt contient des tests et des commandes de vérification qui montrent que le projet a été pensé pour être exécuté localement. La présence de routes de santé, de vues admin d'opérations et de scripts de seed facilite la validation du fonctionnement complet.

Le fichier run-demo.md indique clairement la séquence à suivre : copier l'environnement, lancer Docker Compose, puis exécuter les commandes de seed. Cela réduit les erreurs de mise en route et donne un chemin simple pour la démonstration.

Les points sensibles sont bien identifiés : Qdrant doit tourner pour la recherche, les bases PostgreSQL doivent être disponibles, et les images doivent être correctement indexées avant de lancer une recherche pertinente.

Dans la pratique, ce type d'architecture se valide surtout par parcours complet : login, catalogue, upload d'image, indexation, recherche, puis création de commande. C'est exactement ce que le projet met en place.

14. Bilan du travail

Le projet est cohérent et bien découpé. Chaque service a une responsabilité principale, les API sont simples à comprendre, et la logique de recherche visuelle est isolée du reste. Cela rend le code plus propre et plus facile à maintenir.

Les choix techniques sont adaptés au but du projet : Django pour la structure, DRF pour les API, JWT pour l'authentification, PostgreSQL pour les données métier, Qdrant pour les vecteurs, et Docker Compose pour l'exécution locale. Rien n'est ajouté gratuitement ; chaque outil a un rôle clair.

Le résultat final est aussi intéressant sur le plan pédagogique. On voit comment un vrai système peut être découpé en services plus petits, comment les données circulent, et comment une partie IA peut vivre à côté d'un site e-commerce classique.

15. Conclusion et perspectives

En conclusion, Apex Motors est un bon exemple de projet microservices complet mais compréhensible. La solution montre une séparation nette des responsabilités, une sécurité simple, un mécanisme de recherche vectorielle, et un déploiement local bien organisé.

Si le projet devait évoluer, on pourrait ajouter un meilleur monitoring, des tests d'intégration plus poussés, une documentation API plus formelle et peut-être une interface front plus riche. Mais la base actuelle est déjà solide pour une démonstration académique.

Ce rapport plus long décrit l'ensemble du système, pas seulement un morceau. Il explique ce que fait chaque service, comment ils communiquent, pourquoi certaines décisions ont été prises, et comment l'utilisateur final en profite.

17. Annexe technique : indexation des images

L'indexation commence dans product_service dès qu'une image produit est enregistrée. Le signal Django déclenche l'appel vers search_service. Le service de recherche vérifie d'abord la qualité de l'image, puis il la prépare et calcule un embedding.

Ensuite, le vecteur est inséré dans Qdrant avec des métadonnées utiles : product_id, product_image_id et nom de fichier. Cette information est importante, car elle permet ensuite de relier un vecteur à un produit concret dans le catalogue.

Ce mécanisme est intéressant parce qu'il évite une saisie manuelle. Le vendeur n'a pas besoin de lancer une tâche séparée. L'indexation suit le cycle naturel du produit : création, ajout d'images, puis recherche.

signal post_save -> indexation -> embedding -> Qdrant -> qdrant_id

18. Annexe technique : création d'une commande

La création d'une commande se fait en plusieurs étapes. order_service reçoit le panier, récupère les produits depuis product_service, vérifie que les identifiants existent, puis écrit l'en-tête de commande et les lignes OrderItem.

La présence du snapshot est essentielle. Si le prix change plus tard, la commande garde l'ancienne valeur. Si le produit est renommé, l'ancienne commande reste quand même lisible. C'est ce qui rend le service commande fiable.

Ce choix de conception est simple à comprendre et très utile dans un projet distribué. On ne dépend pas du catalogue en lecture historique. On garde une trace locale de la transaction réelle.

client -> order_service -> product_service -> transaction atomique -> snapshot local

19. Annexe technique : démarrage local

Le fichier run-demo.md montre le chemin le plus simple pour lancer l'application. Il faut copier le fichier d'environnement, démarrer Docker Compose puis lancer les commandes de seed. Le projet est pensé pour être relancé facilement par un autre utilisateur.

Les commandes de seed sont importantes parce qu'elles remplissent la base avec des données utiles pour la démonstration. Sans ces données, on ne verrait pas bien le catalogue, la recherche ni les commandes. Le rapport s'appuie donc sur un projet qui a vraiment été pensé pour être montré.

Le plus pratique est que chaque service reste lançable seul, mais le mode normal consiste à tout lancer ensemble. C'est plus proche d'un vrai environnement d'intégration.

20. Observation finale

Le code est assez propre, mais il reste un projet de démonstration. Il pourrait être renforcé avec davantage de tests d'intégration, une documentation API plus formelle et une vraie interface front plus travaillée. Malgré cela, l'ensemble est déjà très solide pour un projet académique.

Le point fort principal est la séparation claire des responsabilités. On comprend vite qui fait quoi, et la logique reste cohérente du début à la fin. C'est exactement ce qu'on attend d'une architecture microservices bien construite.

En pratique, ce projet montre surtout une chose simple : quand les responsabilités sont bien séparées, le système devient plus facile à comprendre, à faire évoluer et à présenter.

21. Détail de main_service

main_service est la porte d'entrée visible côté utilisateur. C'est lui qui rassemble les réponses, rend les pages principales et coordonne les appels vers les autres services. Son intérêt n'est pas de stocker la logique métier profonde, mais de rendre le système cohérent à l'extérieur.

Le point le plus important est la recherche hydratée. Le service reçoit une image, appelle search_service pour obtenir des identifiants et des scores, puis appelle product_service pour récupérer les champs métiers utiles. Cette étape évite de renvoyer une réponse trop technique au navigateur.

Le service fait aussi le lien avec l'interface web. Il expose les pages de connexion, les pages vendeur, la démonstration et les erreurs personnalisées. Cela permet d'avoir un site lisible, même si l'intérieur est réparti entre plusieurs services.

Dans une architecture comme celle-ci, un gateway est important parce qu'il réduit le bruit pour l'utilisateur final. On ne demande pas au navigateur de comprendre tous les services. On lui donne un seul point d'accès propre et stable.

Ce qu'il assemble

  • Auth via user_service
  • Catalogue via product_service
  • Commandes via order_service
  • Recherche visuelle via search_service

22. Détail de product_service

product_service est probablement le service le plus concret du point de vue métier. Il possède le catalogue, crée les produits, gère les images, et contrôle la propriété du contenu. Tout ce qui touche à la fiche produit passe par lui.

Son design est intéressant parce qu'il mélange du CRUD classique et un traitement d'image léger. Le calcul de miniature, la validation du nombre d'images à la création, et les signaux de post-save montrent que le service ne fait pas seulement du stockage. Il prépare aussi les données pour les usages suivants.

Le service a aussi une relation directe avec la recherche. Dès qu'une image est créée, elle peut être indexée sans action supplémentaire. Cela donne une expérience fluide : le catalogue alimente la recherche, et la recherche reste alignée avec les données du catalogue.

En pratique, c'est ce service qui donne de la matière au reste du système. Sans produit, il n'y a ni recherche utile, ni commande, ni démonstration visuelle intéressante. C'est donc une brique centrale du projet.

23. Détail de search_service

search_service concentre la partie la plus spécialisée du projet. Il n'est pas là pour faire de la logique métier classique. Il sert à convertir une image en vecteur, puis à chercher des vecteurs proches dans Qdrant. C'est le cœur de la recherche intelligente.

Le service est découpé en petites fonctions. La qualité d'image est vérifiée avant tout calcul. Le preprocessing prépare le fichier. L'embedder charge le bon modèle. Qdrant stocke et recherche les vecteurs. Cette séparation rend le code lisible, ce qui est important quand on manipule du ML.

Un autre point important est la gestion du seuil. Le projet ne retourne pas juste les plus proches voisins sans réfléchir. Il applique un filtrage pour éviter les résultats trop faibles ou hors sujet. Cela rend la démo plus crédible et le résultat plus propre.

Dans cette architecture, le service de recherche est volontairement isolé. Il peut évoluer sans casser le reste du système. Si un jour le modèle change, le catalogue et les commandes peuvent rester identiques. C'est exactement le genre de séparation qu'on cherche dans un vrai système distribué.

Ce qu'il fait exactement

  1. Vérifie l'image
  2. Prépare l'image
  3. Calcule l'embedding
  4. Interroge Qdrant
  5. Retourne les matches

24. Détail de order_service

order_service est le service qui fixe l'historique d'achat. Il ne se contente pas de stocker un identifiant de produit. Il copie les informations utiles au moment de la commande, ce qui garantit qu'on gardera une trace exacte de ce qui a été acheté.

Le choix du snapshot est important. En e-commerce, le catalogue peut changer souvent. Un prix peut bouger, une catégorie peut être renommée, une description peut être modifiée. Si la commande ne gardait que l'identifiant, l'historique serait fragile. Ici, il reste stable.

Le service utilise aussi une logique de rôle très simple : seuls les clients peuvent commander. Cela évite les cas ambigus et garde le comportement aligné avec les besoins du projet. C'est une règle facile à expliquer et facile à vérifier.

Ce service montre bien l'esprit du projet : de petites responsabilités, des frontières claires, et des données copiées au bon moment pour éviter les erreurs de cohérence.

26. Synthèse finale des responsabilités

Si on résume le projet en une phrase, on peut dire que chaque service fait une chose précise et une seule, puis parle aux autres par API. Cette idée simple explique presque toute l'architecture. Elle permet de comprendre pourquoi le code reste lisible même si le projet est assez complet.

main_service assemble l'expérience. user_service gère l'identité. product_service garde le catalogue. order_service protège l'historique des achats. search_service donne la capacité de rechercher par image. Qdrant garde les vecteurs. Nginx expose le tout. Cette répartition est nette et facile à expliquer.

Le résultat est un système qui ressemble à une vraie application distribuée, mais qui reste encore lisible pour un rapport universitaire. C'est probablement la meilleure qualité du projet : il est assez riche pour être intéressant, mais assez simple pour être présenté sans se perdre.
