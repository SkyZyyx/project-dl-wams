Runtime-first reading

Five services, one storefront, one visual search pipeline.

This repo is a split Django system for browsing products, authenticating users, creating orders, and running image-based retrieval through search_service. The current architecture is defined by the live code and runbooks, not by the older dual-service sketch in PRD.md.

Runtime topology
5 Django services
Gateway/UI, auth, catalog, orders, and search are split into separate containers and separate Postgres databases.
Cross-service seam
Qdrant hydration
Search returns raw ids and scores; main_service turns those into hydrated product cards by calling product_service.
Persistence pattern
5 Postgres + 1 vector DB
Each Django service owns its relational data. Embeddings live in Qdrant. Product and search share media files through one Docker volume.
Docs drift
Present
The runbooks match the current codebase. PRD.md still describes an earlier two-service architecture.
What to trust first

For architectural decisions, the most reliable sources are docker-compose.yml, END_TO_END.md, the service URL maps, and the proxy/indexing code. They describe the current runtime shape more accurately than the older product spec.

Representative Path

Visual search, end to end

This is the most revealing request path in the repo because it crosses the UI edge, the gateway, the retrieval service, the vector store, and the catalog service before the user sees results. 

sequenceDiagram
    participant B as Browser
    participant N as Nginx
    participant M as main_service
    participant S as search_service
    participant Q as Qdrant
    participant P as product_service

    B->>N: POST /api/search/ + image
    N->>M: forward request
    M->>S: multipart image + limit + threshold
    Note over S: validate quality<br/>preprocess image<br/>embed with active model
    S->>S: out-of-distribution check
    S->>Q: similarity search
    Q-->>S: raw hits {product_id, score}
    S-->>M: matches list
    M->>P: GET /api/products/?ids=...
    P-->>M: product payloads
    Note over M: dedupe by product_id<br/>keep highest scoring image<br/>sort hydrated results
    M-->>B: hydrated product matches
Step 1

Browser posts one multipart request

The storefront JavaScript sends the uploaded image to /api/search/ together with the score threshold and result limit.

main_service/apps/users/static/users/site.js
Step 2

main_service stays thin

The gateway does not embed or rank anything itself. It forwards bytes to search_service and only resumes work after raw matches come back.

main_service/apps/core/views.py
main_service/apps/core/services/search_proxy.py
Step 3

search_service owns retrieval judgment

It validates image quality, crops likely foreground content, embeds the processed image, rejects out-of-distribution queries, and then queries Qdrant.

search_service/apps/search/services/search_use_case.py
Step 4

Qdrant returns ids, not products

Search results are vector hits with scores and payload metadata. They are not user-facing catalog responses yet.

search_service/apps/search/services/qdrant.py
Step 5

Gateway hydrates the catalog view

main_service deduplicates by product_id, keeps the strongest image hit, fetches products from product_service, and merges score fields into the final payload.

main_service/apps/core/services/search_hydration.py
Step 6

The user sees hydrated results only

The browser receives product-shaped search matches, not bare vector ids, which keeps the UI simple but makes the gateway a critical seam.

END_TO_END.md
Friction Points

Where the seams are doing extra work

None of these issues break the design outright, but they do show where callers need to know too much, where data can drift, and where the system becomes harder to test or evolve.

Coupling

Search truth and catalog truth can drift apart

Qdrant may still contain hits for products that no longer hydrate cleanly. The runbook already documents manual collection resets to repair stale ids, which means the seam is operationally visible.

main_service/apps/core/services/search_hydration.py
END_TO_END.md
Leaky edge

Nginx is a mixed gateway, not a single facade

Search goes through main_service, but auth, product, and order routes are also exposed directly through Nginx. A caller still has to know which endpoint family is orchestrated and which is not.

nginx/nginx.conf
Lifecycle

Indexing is best-effort, not guaranteed

Product-image saves and deletes trigger search updates through Django signals. When search is unavailable, the product flow continues and indexing is skipped with a warning.

product_service/apps/products/signals.py
product_service/apps/products/lifecycle.py
Read model

Order reads blur snapshot data and live catalog data

Orders store their own item snapshots, but read responses prefer fresh product payloads when the catalog is reachable. That makes the order view richer, but also less strictly historical.

order_service/apps/orders/serializers.py
order_service/apps/orders/services/order_read_policy.py
Shallow modules

HTTP adapters are duplicated across services

Several small urllib clients repeat the same transport patterns for auth, catalog, and search. They keep dependencies light, but contract changes now fan out to multiple wrappers.

main_service/apps/core/services/search_proxy.py
product_service/apps/products/services/search_proxy.py
Scaling

OOD mean-vector logic grows with collection size

The out-of-distribution check computes a mean vector by scrolling the collection, and the cache is invalidated on each upsert or delete. That is acceptable for demo scale, but it is an early performance pressure point.

search_service/apps/search/services/qdrant_policy.py
Testing and Operations

What is easy to verify, and what is not

The repo tests most service logic at local seams. The tradeoff is that cross-service contract drift tends to show up later, in smoke checks, runbook steps, or manual demos.

Gateway tests

Fast, isolated, mostly mocked

main_service tests patch the search proxy and hydration steps, which makes the UI gateway fast to verify, but means real network contract mismatches are not exercised there.

main_service/apps/core/tests.py
Search tests

Good coverage around the use case core

The search service tests validate quality checks, preprocessing, search decisions, and Qdrant shaping while patching heavy model dependencies.

search_service/apps/search/tests.py
Catalog lifecycle

Signals are covered at the product boundary

The product lifecycle tests verify that image indexing metadata is updated and that delete refreshes reindex the remaining product images.

product_service/apps/products/test_lifecycle.py
Order reads

Snapshot fallback is explicit

The order tests show one of the cleaner seams in the codebase: when the catalog cannot hydrate a product, order responses fall back to stored snapshot data.

order_service/apps/orders/tests.py
Operational read

The runbooks matter because the architecture is real, not decorative.

The stack only behaves like the diagrams when the services, local dataset cache, shared media volume, and active Qdrant collection are aligned. That is why END_TO_END.md spends so much time on index resets, seeding, and smoke checks. Those are not just setup notes; they are part of the system design.

Plain-Language Summary

The shortest accurate explanation

For a non-expert, this is the version that matters: what the system is, what owns what, and where the hard parts sit.

1

The storefront is a coordinator

Users interact with one UI, but the real work is split across dedicated backend services. The main app mostly routes, renders, and assembles responses.

2

The visual search is genuinely separate

Retrieval logic, model selection, preprocessing, and vector search all live inside search_service, which keeps ML concerns out of catalog and order code.

3

The key seam is id-to-product hydration

Search results become user-facing only after raw matches are joined back to product data. That join is the most important handoff in the repo.

4

The design is demo-scale but coherent

The architecture is clean enough to explain and extend, but the rough edges show up where consistency, operational resets, and repeated proxy code start to accumulate.

Built from the current repo shape in docker-compose.yml, END_TO_END.md, the service URL maps, and the search/catalog/order code paths. The older PRD remains useful for intent, but not for the exact runtime topology.
